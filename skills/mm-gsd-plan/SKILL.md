# MM-GSD 规划

输入:先读 `.planning/STATE.md` 与本 phase 的 `*-CONTEXT.md`(已定决策不重新发明;冲突标注)。产出:`.planning/<NN>-<MM>-PLAN.md`(任务数 ≤3 可精简,但**必须落盘**——见"任务四件套"节)。

**PLAN 落盘后跑门禁,转绿才准进执行环节**:

```bash
node ~/.agents/skills/mm-gsd-loop/scripts/gsd-state-check.mjs --plan .planning/<你的文件>
```

它拦的是本文件所有纪律里模型最容易自我放水的那几条:四件套缺项、verify 没有 fails_when 方向、
files_modified 写成模糊措辞(会让 `--worktrees` 的并行保护整个失效)、任务数超预算、action 里塞代码块、
范围缩水措辞、CONTEXT 里没被任何任务引用的 D-NN。**门禁报什么就改什么,不要绕着写**——
它列出的每一项在本文件里都有对应条款。

⚠️ **门禁报错时不要停在那里等人**。`--plan` 列的每一项都是这一份 PLAN 自己能改的,改完重跑。
只有两类情况才停下来:**要改的决策会推翻 CONTEXT 里已锁定的 D-NN**(需求变更),或者
`--plan` 报的错需要动别的 phase 的工件(超出本步职责范围)。其余一律自己修掉继续走。

规划前如果 phase 清单刚定过,先跑 `--phases` 看波次:同一波次的 phase 会并行,它们的 files_modified
必须零重叠,现在发现冲突比合并时便宜得多。

**工件落点与归属**:`.planning/*` 是 agent 本地工作流记忆(STATE/CONTEXT/PLAN/SUMMARY/VERIFICATION),**本地不入库、不 push 远程**;项目 `.scratch/<主题>-<日期>/` 是**业务票面**(缺陷票/设计稿票),要入库共享给团队(该目录常被 git exclude,需 `git add -f`)。两者不可混放:流程记忆进 `.planning/`,业务产出进 `.scratch/`。

## 拆票(两层)

**Phase 票 = 可独立验证的目标切片**:一个 phase 做完,用户能做一件之前做不了的事;做不到就不算完整 phase。
- **垂直切,不水平切**:功能贯穿到底(路由→handler→数据→界面),不"先做完全部后端再做前端"——水平切的每个 phase 都无法验证,验证不了就要靠猜。
- 预估超过一个执行上下文(~50%)→ 拆成两个 phase,不删内容不压任务。
- 新项目 phase 01 固定为 walking skeleton(最薄可运行骨架,技术选型集中在此定)。

**Plan 票 = 一个执行上下文一次跑完的量**:
- 2-3 任务/plan;>3 任务或跨多个子系统 → 拆;单任务 >5 文件 → 拆。
- 每张票可**独立提交、独立验证**(有自己的 fails_when)——拆票拆得对,单张票失败不传染。
- 依赖只指向更早的票;并行执行的票**零文件重叠**(files_modified 声明就是并行的安全契约)。

**一张 PLAN 就是一批**(执行端按批收尾,不是按票):
- 批内用 frontmatter 的 `wave` 标同批;**同批必须零文件重叠**,撞了就拆批(重叠的两个票并行必冲突)。
- 批级检查写在 frontmatter 的 `batch_verify`(可以全量):**这一批跑一次**,失败**一次修完**再跑一次(≤2 轮)。
- **一票 = 一个子代理**:一张票的量 = 一个子代理 **20 分钟**能做完的量(≤5 文件、≤1 条 verify);超了就拆票。
- 票级 `<verify>` 只跑**本票的便宜检查**(具名测试/单文件/单入口);全量套件进 `batch_verify`。
- ≤3 任务的小 phase 可内联进执行 prompt,不生成独立 PLAN 文件(省一轮读写)。

## 预授权决策清单(减少执行期提问)

PLAN 里单列一节 **`<auto_decisions>`**:把"执行期可能需要问用户的点"在**规划时**就查清项目事实并定夺,标 `[AUTO]` + 一句依据(为什么这么定、依据是哪个文件/约定)。执行期照做不再问。
预授权只覆盖拍板权五类**之外**的点(库、文件组织、命名、实现路线、测试写法);五类白名单里的不预授权——那是真的该问用户。
用户事后可在 CONTEXT/PLAN 里推翻 `[AUTO]` 条目;推翻算需求变更,走下一轮讨论。

## 目标倒推(goal-backward)

从 phase 目标反推,不从功能列表正推:
goal(结果形,不是任务形)→ 可观察 truths(3-7 条,用户视角:"密码是安全的"✓ / "bcrypt 已安装"✗)→ artifacts(哪些东西必须存在)→ 连线(谁接谁)。
**回退**:计划里记一句"这个 phase 怎么回退"。

## Tracer-first 垂直切片

- 首任务 = 贯穿所有层的**最薄端到端路径**,生产质量非原型(功能可以缺,架构不可以缺)。
- 每个任务完成后,用户能做之前做不到的事。"只打地基/只铺基础设施"是伪装的水平切分——重构。

## 任务四件套(每个任务必填)

- `<files>`:精确路径,禁止"相关组件"类模糊语
- `<read_first>`:**要改的文件必读**;「作为真理来源的文件」(接口定义、类型声明、既有同类实现)是**核对点**——
  执行者读它只为确认图纸与现状一致,不是从头理解项目。**规划期就该把要核对的东西摘进 `<action>`**,
  摘得越清楚,执行端要打开的文件越少(施工图要有料,不能只有路径)
- `<action>`:做什么 + **避免什么及为什么**;不含代码块
- `<verify>`:自动化验证命令
- `<done>`:可度量的完成判据

**任务数 ≤3 时可以不展开成完整 PLAN,但仍要落一个精简 `*-PLAN.md`**(每任务一行四件套)——验证环节靠它逐条对 verdict,状态机靠它推进;不落盘 = 闭环断裂。

**fails_when 契约**:每条 `<verify>` 命令后必须紧跟失败方向——失败时看到什么(退出码/输出串/缺失行)。写 TBD/N-A/none 直接视为没写。没有失败方向的验证是假验证。
可选 `<precondition>`:一行可检验的前置事实(文件在/命令可用),执行者动手前先断言,不满足即停——防在错误前提上施工。
**验证命令复用**:上一 phase 实际跑通过的验证命令,逐字复制进新 plan,不重新推导路径(重新推导是验证命令失效的高发原因)。
每个 plan 另列 `files_modified`(新增/修改/删除全清单)与 `depends_on`(只指向更早的任务;同批并行的任务零文件重叠)。

**跨 worktree 时的 files_modified 是安全契约,不是元数据**:见 mm-gsd-loop 的「多 worktree 并发」。写法上必须是**机器可解析**的行内数组或 YAML 列表,`files_modified: 相关模块` 这类模糊语会让 `--worktrees` 检查直接失效,等于没有并行保护。

**实测仲裁**:计划文档与实测冲突时,实测为准——实测证实计划 → 照做但警告文档过期;实测反驳计划 → 打回,附实测值;无法实测 → 报差异,不替任何一方定对错。

## 验收反模式(出现即打回)

- 禁止主观语:"looks correct"/"works properly"/"完成该功能"
- grep 卫生:`grep -c` 会数注释,用 `grep -v '^#' | grep -c token`;禁裸 `== 0` 门
- 验证字面量不得出现在 action 正文(否则执行者照抄造绿)
- `|| true` / `2>/dev/null || echo 0` 喂比较 = 假验证

## 决策保真(D-NN)

CONTEXT.md 每条 D-NN 决策必须被本 phase **至少一张票认领**并精确实现;矛盾 → 停下问人。deferred 条目不进计划。

**一张票的 `covers` 只写它真做的决策** —— 核销是 phase 级 union:本 phase 所有票的 covers 并集
必须覆盖 CONTEXT 的全部决策,少一条那道 phase 级门会指名报红。判据只扫 `covers` 字段,
正文里提到 D-NN 不算认领(「提到」不等于「认领」)。

为什么不让每张票都写全 phase 的决策:那会逼着只做三分之一的票也把不相关决策写进去,
填出来的 covers 与「记账不全」是同一类病 —— 看着齐全,其实没读。纯实现票(重构、修 bug、补文档)
更是被这条逼着去引用一条它根本没碰的决策。

## 缩水禁令

计划中出现 v1 / simplified / for now / placeholder / basic version / minimal implementation / skip for now / will be wired later = 范围缩水,重写。规划者无权判定"太难"——只有三个正当拆分理由:上下文装不下、信息缺失、依赖冲突。

技术选型(库/文件结构/命名/实现路线)按项目既有模式自己定,在计划里标 `[AUTO]` 注明依据;只有 mm-gsd-loop「拍板权」五类白名单(产品取舍/破坏性/付费/合规/只有用户知道的输入)才停下来问用户。

## 多源覆盖审计(定稿前必做)

四源对照:GOAL(目标)/ REQ(需求清单)/ RESEARCH(有条件必经)/ CONTEXT(决策)。任何一项 MISSING → 显式报告并决定(补任务/移下一 phase),**绝不带缺口静默定稿**。
**缺口里的需求问题回 `mm-gsd-discuss`** —— 用户拍板是讨论期的活,不是规划期的活。你替用户拍板 = 把一个本该被问的问题悄悄定成了技术默认,用户再也看不见它。

**RESEARCH 不是「如做了」**:满足任一触发条件就必须研究 —— files_modified 跨 ≥3 个顶层目录 / 触及 git 历史里从未改过的目录 / goal 明写「深入了解」。触发条件成立 → 写 `.planning/<NN>-RESEARCH.md`(读到了什么、因此决定了什么,至少一条 file:line 引用);不成立 → 审计表里写「不适用:<理由>」。检查器 `--plan` 按同一套条件判红。
**研究谁做**:触发研究时**派一个只读子代理**去查,主上下文只拿**摘要 + 落盘路径** —— 别把探查结果灌进主上下文
(那是击穿上下文最常见的方式)。研究产物要带 `## 摘要` 节且**不超过 15 行**,超了就说明摘要在复述全文。
**研究产物要有下游**:研究写完,把**用到的结论摘进票的 `<action>`** —— 执行端照的是票,不是研究文件。
研究文件仍要在票的 `<read_first>` 或 `<action>` 里**点名**(检查器认这个):不点名 = 研究落盘了没人读,执行端会自己重查一遍。

## 预算

2-3 任务/plan;>3 任务或多子系统 → 拆;单任务 >5 文件 → 拆;整个 plan 目标 ~50% 执行上下文。装不下 → 拆 phase,不删内容。
**一票一代理**:一张票 = 一个子代理 20 分钟能做完的量(≤5 文件、≤1 条 verify);超了就拆,别把长活塞给一个子代理。

## 规划者失效模式(你会怎么偷懒,逐条自查)

1. **"执行时再说"**——文件清单不全、依赖不声明、验收标准写"看情况"。执行期要猜的东西一律现在写清。
2. **预算超了就缩内容**而不拆票("先做个简化版"= 缩水禁令);正解是拆。
3. 验收标准写自己能读懂的,不是能跑的(测试名/命令/CLI 输出)。
4. 难的任务推到执行期"到时候再看"——难是拆票的理由,不是推迟的理由。
5. 复制上一 phase 的 verify 命令,不看它在当前上下文还成不成立。
6. 决策保真偷懒:D-NN 只提一句不复述精确语义,执行时按自己的理解实现。
7. 依赖/文件重叠没算清,并行计划互相踩文件(同 wave 零重叠是硬约束)。

## 完成后

- 例外:`--plan` 没转绿就进执行,是拿一份执行者猜不出来的契约开工。报错里都写着该改什么,先改;真要改决策才回 mm-gsd-discuss。
