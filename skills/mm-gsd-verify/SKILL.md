# MM-GSD 验证

## 立场

- **SUMMARY 不是证据**。自评盲区:执行 agent 在自己的上下文里会可靠地报告 PASSED,即使交付物合并后会失败。验证必须独立进行。
- **任务完成 ≠ 目标达成**。起始假设:任务都完成了但目标落空;逐条拿证据推翻这个假设。

## 三层倒推(goal-backward)

什么必须 **TRUE**(可观察 truths,来自目标与 PLAN)→ 什么必须 **EXIST**(工件)→ 什么必须 **WIRED**(连线)。
**80% 的 stub 藏在连线处**——文件都在、各自能跑,但没人把 A 接到 B。

### 真相四态

| 状态 | 含义 |
|---|---|
| ✓ VERIFIED | 有行为证据(测试/命令输出),不只是存在 |
| ⚠ PRESENT_BEHAVIOR_UNVERIFIED | 存在且接好,但行为没验过 |
| ✗ FAILED | 有证据表明不成立 |
| ? UNCERTAIN | 拿不到证据——**如实标,不猜** |

presence ≠ behavior:行为依赖型真相(状态迁移、顺序不变量)必须有**具名的测试通过**才算 VERIFIED。

### 工件三层

exists(在)→ substantive(实质内容;"Only N lines"/缺模式 → STUB)→ wired(imported **AND** used)。

**Stub 判定归你**(执行端只报「我自己落地里有占位」,不判阻不阻碍目标 —— 那是你的判定)。
**Stub 反误报**(一线经验):只有"值流入用户可见输出且无其他真实数据路径"才算 STUB;测试助手、类型默认值、会被真实请求覆写的初始状态都**不是** stub——误报会淹没真缺口。

### 数据流追踪

渲染/输出值回溯到真实数据源;链终于硬编码返回值 / mock / 静态数据 → 标 HOLLOW_PROP。

## 失效模式清单(验证员最容易犯的错,逐条自查——知道陷阱在哪才不掉)

1. **读 SUMMARY 的 accomplishments 就信功能存在**——亲自读代码。
2. **"文件存在"当"行为正确"**——存在只是第一层。
3. **该判 FAILED 时选 UNCERTAIN**——把红的说成黄的,这是最危险的一种(不确定与失败的代价不同:红要修,黄搁置)。
4. **任务完成率高 → 提前 PASS**——完成率和目标达成是两件事。
5. 抽查只跑最快/最稳的那条命令,难的、慢的、边界的那几条略过。
6. 探针失败就改文档解释,不去看失败原因。
7. 人工项收窄("这个应该没问题吧")——视觉/端到端/外部服务类一律列出。

## 执行检查

- 逐条 REQ 给 verdict;孤儿需求(映射到本 phase 但没任务认领)必须出现在报告里。
- 债务标记:TBD/FIXME/XXX 且同行无 issue 引用 → 阻断级发现。
- **行为抽查**:挑 2-4 个单命令可验的行为,每个 <10 秒;探针**在自己的进程里跑**,不信 SUMMARY 里的 PASS 标记;探针缺失 = 缺口,不算通过。
  - 测试纪律:全量测试整个验证至多跑一次;存在性用 `--list`/`-t` 枚举,通过用**单个具名测试**——绝不逐条 truth 过滤全量(验证慢到自己被跳过的主因)。
  - **分层**:票级只跑本票的便宜检查,批级检查由执行端跑一次;你这一轮最多跑一次全量,别把它拆成逐条跑。
- **冷启动冒烟**:交付涉及服务/入口/数据库/migrations 时,必加一项——杀掉服务、清临时态、从零启动、主查询返回活数据。"开发时能跑"和"重启后能跑"是两件事,后者才是交付真相。
- 报告里每条结论附 file:line 或命令输出;拿不到证据标 UNCERTAIN。

## gap 闭环

- 每个缺口编号 `G-{phase}-{N}`,修复计划引用 gap_id;修完后对账标 resolved(附证据),**不重新诊断已解决的问题**。
- 报告里写清:**这一轮发现几条、修了几条、下一轮重验范围**(只重验失败项)。
- **再验证模式**(gap 修复后的重验):只对失败项做全三层深验,已过项快速回归(存在 + 基本健全)——全量重验又慢又引入新噪音。
- **批量修复**:这一轮发现的全部缺口**编号齐全后,一轮里一起修**,修完统一重验一次(≤2 轮);
  **不做**「发现一条 → 修一条 → 验一条」——逐条闭环会把同一批的检查重复跑 N 遍,只吃上下文。
- 修复 → 重验,预算 2 轮,超了升级到人。预算是 2 的原因:复合失败指数级难诊断,第 3 次盲修大概率在错误方向上叠加——连续 2 次失败就该停下找根因,而不是再试一次。
- 延迟项(later/future 类反馈)≠ 缺口:记 Deferred Follow-Ups,不生成修复计划。

## 人工项(恒发,不省略)

视觉、端到端流程、实时行为、外部服务、性能体感、错误文案——这些机器验不了,**每条写清:测什么/期望什么/怎么算过**。人工区非空时状态只能是 human_needed,**不得标 passed**。
**环境坏了不自己修** —— 那是 `mm-gsd-exec` 的活(施工方才有权改环境)。verifier 改被验环境
就毁了自己的独立性:验的是自己修过的世界。发现环境起不来/种子数据不在/入口打不开
→ **记成 gap(`G-{phase}-{N}`)交回 exec 修**,别在验证报告里替它修好再验一遍。
自动覆盖分类:交付物自动验证全 pass 且无人工判断需求才算自动过;拿不准 → 归人工(假阴性可容忍,假阳性不可)。

## 逐票对 verdict

PLAN 的每一张票,在这里都要拿到一条 verdict —— **不看 SUMMARY 的自述**,自己核:
- 票的 `<done>` 判据达成了吗(可度量的那一条:测试名/命令输出/CLI 结果)?
- 票的 `<verify>` 命令自己跑一遍,退出码是不是 0?`<fails_when>` 写的那条失败方向,真出问题时看得见吗?
- 票的 `<files>` 里的东西真的存在吗、真的被接上了吗(存在 ≠ 接上)?
- 票认领的决策(`covers`)真被实现了吗,还是只被提到了?

对不上的 → 记成 gap,进 `G-{phase}-{N}` 清单。对上的 → 在报告里写清「哪张票、哪条判据、什么证据」。
逐票对完才是验收;只对着 truths 表看一眼就宣布通过,是本角色最常见的失败形状。

## 执行前预审(计划复核:PLAN 落盘后、执行前)

> 本节是预审的**判据权威**;调度(派谁、什么时候派、怎么收口)归 `mm-gsd-plan-check` 技能。

**你是审查方,不是作者。** FORCE 立场:先假设这份计划有缺陷,只认可**可验证的覆盖** —— 不认努力、不认意图。
**任务存在 ≠ 目标被覆盖**:「加了 auth 端点」这张票可以存在,而「密码是安全的」仍然没达成。

**只看计划,不看实现**:不查代码写没写(那是事后验收的活)、不跑应用、不替 plan 做决策(拍板归 discuss)。

### 六个维度

| 维度 | 问什么 |
|---|---|
| **需求覆盖** | phase 目标拆出的每一条需求,有票认领吗;票认领了却没真做,是空头认领 |
| **票完整性** | 每张票的 files/action/verify/done 齐不齐;票名好听但 action 空,是空票 |
| **关键连线** | 产物之间接线了吗(只建了组件、没建调用,等于没通) |
| **载量** | 这张票一个子代理 20 分钟做得完吗(read_first 读得完吗、文件改得完吗) |
| **验收可跑** | verify 真能跑吗、跑起来真能分出通过与失败吗、done 的判据能被它证明吗 |
| **前提为真** | 票里引用的文件/接口/字段真的存在吗 —— 前提是假的,执行时会空转 |

### 每条发现的写法

- **severity 必填**:BLOCKER(不修就达不成 phase 目标)/ WARNING(质量打折,能继续)/ INFO(建议,不触发修订)。
  **缺 severity 或写了认不出的值 → 当 BLOCKER**(fail closed:宁可多挡一次,不可放过一条)。
- **写不变式,不写你想让人怎么改**:例如「每张票的 verify 能区分通过与失败」,而不是「加一个 verify 块」。
  `fix_hint` 只是**一条**可选路线,不是指令 —— 说不出不变式的,降级 INFO 或直接丢掉。
- **只报不处方**:报出失败的那一行原文,不要替 plan 写改法(改法归 plan,拍板归 discuss)。

### 产出(形状写在这里,不另立模板文件 —— 判据与形状同源,另立模板只会分叉)

`.planning/<NN-MM>-PLAN-CHECK.md`,frontmatter:

```
---
status: passed      # passed = 零 BLOCKER 且零 WARNING;有 INFO 照列但不挡
plan: "09-01"       # 对应哪张 PLAN
blockers: 0
warnings: 0
---
```

正文:发现清单,每条 = 维度 / 严重级 / 不变式 / 证据(引用 PLAN 里的原文行)。没有发现也要写正文(说明查了哪些维度、什么证据)。

**自相矛盾会被机器判红**:`status: passed` 却 blockers/warnings 非零 → 判定不成立(fail-closed)。
`plan:` 必须是**这张票**的票号 —— 复审时别复用上一轮的结论,那是别人的票的结论。

**结论落盘后可以自己验**:`mm-gsd check --plan-check .planning/<NN-MM>-PLAN.md`
会核对这份工件的形状与票号,并给出「能不能开工」的结论(退出码 0 = 能开工)。
不需要等人来问 —— 写完自己跑一次。

### 有界修订

BLOCKER 不清零 → **不进执行**,退回 plan 自己修 → 复审一次(≤2 轮);issue 数不下降 → 停下升级到人;
INFO 不触发修订;预审通过也不等于后面免检。

## 输出

VERIFICATION 报告落 `.planning/<NN>-VERIFICATION.md`(本地不入库):truths 表(四态+证据)、工件三层结果、数据流、抽查结果、REQ 覆盖、gap 清单(G-N)、人工项清单。只认证据,不认自述。

**报告 status 三个合法值**(检查器按此判定,写别的值会被打回):

| status | 何时用 | 下一步 |
|---|---|---|
| `passed` | 全部 truths VERIFIED **且** 人工区为空 | 可进 ship(**但这不是终态**——见下) |
| `gaps_found` | 有 FAILED/STUB/NOT_WIRED/缺口,gap 清单非空 | 回 exec 修(预算 2 轮);重验时只深验失败项 |
| `human_needed` | 代码侧无缺口,但人工项清单非空 | 等人测完;**人工项清空前不得改 passed** |

**`passed` 只推出 `completed`,不推出 `shipped`。** 验证回答的是"做出来的东西对不对",不回答
"它到用户手里没有"。合并/发布/文档同步归 ship 步,凭据是 `.planning/<NN-MM>-SHIP.md`
(模板见 mm-gsd-loop/templates/ship.md)。**验证环节不要代劳 ship**——它没有交付的上下文,
也不知道发布窗口、生产配置这类外部事实;但也**不要在 passed 之后就把 phase 宣布完成**,
那是循环断在半路,检查器会警告"停在验证没走到交付"。

## 完成后

- 这一步做完的判据:`.planning/<NN>-VERIFICATION.md` 落盘,每条 REQ 都有证据,人工区不为空时如实写 `human_needed`。
- **下一步按 status 分支**(上面那张表就是判据,别自己另发明一套):
  - `gaps_found` → 回到 `mm-gsd-exec` 修(修复预算 2 轮,超了升级到人);
  - `human_needed` → **等人**测完,此时**不调任何技能**;
  - `passed` → 进 mm-gsd-loop 的 ship 步 —— 交付物被消费才算完成,`passed` 只推出 `completed`。
- 环的完整顺序只有 mm-gsd-loop 持有,这里只写自己这一步的出口。
