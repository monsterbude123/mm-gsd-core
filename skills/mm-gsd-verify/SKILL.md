# MM-GSD 验证

## 立场

- **SUMMARY 不是证据**。自评盲区:执行 agent 在自己的上下文里会可靠地报告 PASSED,即使交付物合并后会失败。验证必须独立进行。
- **任务完成 ≠ 目标达成**。起始假设:任务都完成了但目标落空;逐条拿证据推翻这个假设。

## 三层倒推

什么必须 **TRUE**(可观察 truths,来自目标与 PLAN)→ 什么必须 **EXIST**(工件)→ 什么必须 **WIRED**(连线)。
**80% 的 stub 藏在连线处**——文件都在、各自能跑,但没人把 A 接到 B。

### 真相四态

| 状态 | 含义 |
|---|---|
| ✓ VERIFIED | 有行为证据(测试/命令输出),不只是存在 |
| ⚠ PRESENT_BEHAVIOR_UNVERIFIED | 存在且接好,但行为没验过 |
| ✗ FAILED | 有证据表明不成立 |
| ? UNCERTAIN | 拿不到证据——**如实标,不猜** |

presence ≠ behavior:行为依赖型真相(状态迁移、顺序不变量)必须有**具名的测试通过**才算 VERIFIED。

### 工件三层

exists(在)→ substantive(实质内容;"Only N lines"/缺模式 → STUB)→ wired(imported **AND** used)。

**Stub 反误报**(一线经验):只有"值流入用户可见输出且无其他真实数据路径"才算 STUB;测试助手、类型默认值、会被真实请求覆写的初始状态都**不是** stub——误报会淹没真缺口。

### 数据流追踪

渲染/输出值回溯到真实数据源;链终于硬编码返回值 / mock / 静态数据 → 标 HOLLOW_PROP。

## 失效模式清单(验证员最容易犯的错,逐条自查——知道陷阱在哪才不掉)

1. **读 SUMMARY 的 accomplishments 就信功能存在**——亲自读代码。
2. **"文件存在"当"行为正确"**——存在只是第一层。
3. **该判 FAILED 时选 UNCERTAIN**——把红的说成黄的,这是最危险的一种(不确定与失败的代价不同:红要修,黄搁置)。
4. **任务完成率高 → 提前 PASS**——完成率和目标达成是两件事。
5. 抽查只跑最快/最稳的那条命令,难的、慢的、边界的那几条略过。
6. 探针失败就改文档解释,不去看失败原因。
7. 人工项收窄("这个应该没问题吧")——视觉/端到端/外部服务类一律列出。

## 执行检查

- 逐条 REQ 给 verdict;孤儿需求(映射到本 phase 但没任务认领)必须出现在报告里。
- 债务标记:TBD/FIXME/XXX 且同行无 issue 引用 → 阻断级发现。
- **行为抽查**:挑 2-4 个单命令可验的行为,每个 <10 秒;探针**在自己的进程里跑**,不信 SUMMARY 里的 PASS 标记;探针缺失 = 缺口,不算通过。
  - 测试纪律:全量测试整个验证至多跑一次;存在性用 `--list`/`-t` 枚举,通过用**单个具名测试**——绝不逐条 truth 过滤全量(验证慢到自己被跳过的主因)。
- **冷启动冒烟**:交付涉及服务/入口/数据库/migrations 时,必加一项——杀掉服务、清临时态、从零启动、主查询返回活数据。"开发时能跑"和"重启后能跑"是两件事,后者才是交付真相。
- 报告里每条结论附 file:line 或命令输出;拿不到证据标 UNCERTAIN。

## gap 闭环

- 每个缺口编号 `G-{phase}-{N}`,修复计划引用 gap_id;修完后对账标 resolved(附证据),**不重新诊断已解决的问题**。
- **再验证模式**(gap 修复后的重验):只对失败项做全三层深验,已过项快速回归(存在 + 基本健全)——全量重验又慢又引入新噪音。
- 修复 → 重验,预算 2 轮,超了升级到人。预算是 2 的原因:复合失败指数级难诊断,第 3 次盲修大概率在错误方向上叠加——连续 2 次失败就该停下找根因,而不是再试一次。
- 延迟项(later/future 类反馈)≠ 缺口:记 Deferred Follow-Ups,不生成修复计划。

## 人工项(恒发,不省略)

视觉、端到端流程、实时行为、外部服务、性能体感、错误文案——这些机器验不了,**每条写清:测什么/期望什么/怎么算过**。人工区非空时状态只能是 human_needed,**不得标 passed**。
把人工项交给用户前,agent 先自查环境:服务起得来、种子数据在、入口可访问——**绝不带着坏环境请人验证**(用户点开一个起不来的服务,验证就废了)。
自动覆盖分类:交付物自动验证全 pass 且无人工判断需求才算自动过;拿不准 → 归人工(假阴性可容忍,假阳性不可)。

## 输出

VERIFICATION 报告落 `.planning/<NN>-VERIFICATION.md`(本地不入库):truths 表(四态+证据)、工件三层结果、数据流、抽查结果、REQ 覆盖、gap 清单(G-N)、人工项清单。只认证据,不认自述。

**报告 status 三个合法值**(检查器按此判定,写别的值会被打回):

| status | 何时用 | 下一步 |
|---|---|---|
| `passed` | 全部 truths VERIFIED **且** 人工区为空 | 可进 ship(**但这不是终态**——见下) |
| `gaps_found` | 有 FAILED/STUB/NOT_WIRED/缺口,gap 清单非空 | 回 exec 修(预算 2 轮);重验时只深验失败项 |
| `human_needed` | 代码侧无缺口,但人工项清单非空 | 等人测完;**人工项清空前不得改 passed** |

**`passed` 只推出 `completed`,不推出 `shipped`。** 验证回答的是"做出来的东西对不对",不回答
"它到用户手里没有"。合并/发布/文档同步归 ship 步,凭据是 `.planning/<NN-MM>-SHIP.md`
(模板见 mm-gsd-loop/templates/ship.md)。**验证环节不要代劳 ship**——它没有交付的上下文,
也不知道发布窗口、生产配置这类外部事实;但也**不要在 passed 之后就把 phase 宣布完成**,
那是循环断在半路,检查器会警告"停在验证没走到交付"。
