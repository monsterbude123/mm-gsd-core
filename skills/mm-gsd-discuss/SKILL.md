# MM-GSD 讨论(决策捕获)

## 立场

- **思考伙伴,不是采访者**:用户是愿景者——知道要什么、视觉偏好、优先级、什么算成功;你懂实现。只捕获**用户在意且有多个合理答案**的决策(灰区),不把设计工作推给用户,也不替用户做价值判断。
- 用户知道的:视觉/偏好/优先级/成功标准。**不该问的**:代码模式、技术风险、实现路线(那是 plan 的事)。
- **捕获完成标准**:planner 和 executor 拿到 CONTEXT 后,**不再需要追问用户任何问题**。写完自检一遍:还有没有"用户其实在意、但我没问"的口子——漏掉的决策不会消失,它会在执行期变成偏差或返工。

## 灰区识别

- 灰区 = 影响结果且多解的实现决策。从本 phase 的**领域**生成,禁用通用标签("UI/UX 怎么做"✗;"导出是同步阻塞还是后台任务"✓)。
- 数量:2-4 个灰区,每个 ≤2 问;全部清晰 → 明说"无灰区",不硬凑问题。**即便全部清晰也要落一个最小 CONTEXT.md**(记"无灰区,决策已全在项目文档"+ 指向那些文档)——检查器靠 CONTEXT 的存在推进状态机,不落盘就永远卡在 discussing。
- 每个灰区给 3-4 个具体选项,各带一句代价/好处;**不提供"你决定/跳过"选项**——逃逸口会废掉整份决策记录。
- **第 5 个灰区的出口**:灰区超过 4 个 → **全部落盘、报用户裁决优先级**,不算违规 —— 截断违背捕获完成标准。

## 不重问已决

- 先加载既有决策:STATE 的 Decisions 节、已有 CONTEXT 的 D-NN。已决的**预填**("phase 01 你选了 JWT,沿用还是改?"),不是从头再问;与既有决策冲突 → 显式指出让用户裁决。
- 用户回答中引用的任何文档/spec/issue → 立即读,记入 CONTEXT 的 canonical refs(后续 plan 的验证命令可直接引用)。

## 需求全量落盘

- **每条诉求都要有归宿**:**落成 REQ-N 条目**(归宿是需求的)、**进候选纪律**(归宿是纪律的)、**记 deferred**(明确暂不做的)三者选一,不许无归宿。归宿是 REQ 的**追加**进 `.planning/REQUIREMENTS.md`(不覆盖已有条目),格式:`- REQ-N: <需求一句话>`,一行一条。没有 REQUIREMENTS.md 时由 discuss 创建。
- 分工:**REQ = 要达成什么**(用户说的,REQUIREMENTS.md 承载);**D-NN = 怎么定**(拍板定的,CONTEXT 承载)。不要把 REQ 写进 CONTEXT,也不要把「要不要拍板」的事项写成 REQ —— 那是 D-NN 的活。
- 漏落的代价:REQ 不在清单里,后面整条链路(票 covers 认领 → checkReqCoverage 覆盖门 → verify 预审)都对不上它。落盘时自检一遍:还有没有"用户提了、REQ 清单里没有"的口子。
- REQ-N 落盘后进确认门复述清单(见下「确认门」)—— 复述以 REQUIREMENTS.md 落盘内容为准,不在会话里另存一份。

## 深挖需求(落 REQ 前必做)

每条用户诉求写成 REQ 之前先答**四问** —— ①真实需求:背后那个用户动作是什么;②谁消费:谁在什么时候看它或用它;③什么时候会废:什么情况下这东西没人用;④做完长什么样:可观察的结果。答案写进 `.planning/<NN>-CONTEXT.md` 的 `<mining>` 节,每条 REQ 一块,四个标签行:`- **真实需求**: ` / `- **谁消费**: ` / `- **什么时候会废**: ` / `- **做完长什么样**: `,逐条非空。机器门 `checkRequirementMining` 在 `--plan` 时核对,缺一问判红;豁免:没有 `<mining>` 节的既有项目照旧(baseline 与 req-ledger 已处置的 REQ 不判)。

## 产出 `.planning/<NN>-CONTEXT.md`(模板见 mm-gsd-plan/templates/context.md;本地不入库)

**文件名必须带 phase 前缀**,不能叫 `CONTEXT.md`。检查器两处都只认 `-CONTEXT.md` 后缀(`pick("-CONTEXT.md")` 与决策保真门),写成裸名会**静默失效**,状态机卡在 discussing。

- **D-NN 决策要具体**:好 = "卡片式布局,不用时间线";坏 = "现代简洁"——追问到具体为止,模糊决策等于没决策。
- **每条 D-NN 必须标可逆性**:`reversible` / `costly` / `one-way`,标 `one-way` 的要举证(指名 migration、已发布契约或外部依赖系统)。**没说清可逆性的决策不算被决策过** —— 规划期门禁会直接判红。
- **deferred 兜住范围蔓延**:用户提到的"以后能不能…"全部落进 deferred(不丢、不实施);规划阶段禁止实现 deferred 条目。
- phase 边界来自目标,固定:讨论只澄清 HOW,不加新能力(要加 → 记 deferred)。

## 快速通道

已有 PRD/验收文档/需求单 → 读文档直接抽取决策 + 只问文档**没回答**的灰区,不从零问起。文档与用户口头冲突 → 用户最新口径为准,记一条 D-NN 说明覆盖。

## 用户批注消化(开头必做)

讨论开始前先读 `.planning/annotations.json`(用户落盘的审核意见);`.planning/annotations.json` 不存在 = 没有待消化批注，直接继续。**status=open 的批注按 type 消化**,消化后把该条 status 改 digested —— 不消化,检查器默认模式会一直黄提醒「N 条用户批注待消化」。

- **需求遗漏** → 按批注内容草拟 REQ 追加进 REQUIREMENTS.md,走下面的确认门复述;
- **方向不对** → 作为本次讨论的输入重开对应决策,推翻的 D-NN 在 CONTEXT 里改写并注明日期;
- **备注** → 记录参考(进 CONTEXT 的 specifics),不改决策;
- **验收不过** → 不在讨论期修,走 mm-gsd-loop 的「点修」分流(不新增 REQ + 不改 D-NN + ≤5 文件 → R 票)。

## 批注分流表(diagnose / repair / requirement / note)

一键批注(作业型)带 action 字段,消费端按 action 分流到四条去处:

- **diagnose** → 诊断(未收口 phase 的排查;已交付 phase 的细节走 repair);
- **repair** → 点修 R 票(照 mm-gsd-loop 的「点修」节);
- **requirement** → 补 REQ(草拟后走确认门);
- **note** → 记参考(进 CONTEXT 的 specifics)。

没有 action 的老批注仍按 type 消化:需求遗漏→补 REQ / 方向不对→重开决策 / 验收不过→点修分流 / 备注→记参考。
消化完把结论摘要回填到该批注的 note 字段,并把 status 改成 digested。

## 确认门

- REQUIREMENTS.md(REQ 清单)与 `<NN>-CONTEXT.md`(D-NN)两份工件**都落盘后**,把 **REQ 清单(每条一行)+ 每条决策一句话**复述给用户;**用户确认后才准调用 mm-gsd-plan**。复述时要把**深挖结论一起复述**(四问答案跟着 REQ 走),只复述需求原话不算过。不复述全文 —— REQ 一行 + 决策一句话,长文用户不读。
- 用户纠正 → 修订工件后再确认;确认没过,收尾不算完成。
- fast 通道(不建 REQ/CONTEXT)免确认 —— 没有工件就没有要确认的账。

## 完成后

- 这一步做完的判据:决策都落成 `.planning/<NN>-CONTEXT.md` 里的 D-NN,`deferred` 收住了范围蔓延,且**确认门已过**(用户确认后才准调用下一步)。
- **下一步:调用 `mm-gsd-plan`** —— 把 CONTEXT 变成可执行的 PLAN。
- 例外:决策已全在 CONTEXT、且只是纯基础设施或实现路径清晰 → 讨论可以跳过(见 mm-gsd-loop 的「五步成环」),直接进 `mm-gsd-plan`。
- 环的完整顺序只有 mm-gsd-loop 持有,这里只写自己这一步的出口。
