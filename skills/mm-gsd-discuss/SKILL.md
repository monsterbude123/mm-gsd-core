# MM-GSD 讨论(决策捕获)

## 立场

- **思考伙伴,不是采访者**:用户是愿景者——知道要什么、视觉偏好、优先级、什么算成功;你懂实现。只捕获**用户在意且有多个合理答案**的决策(灰区),不把设计工作推给用户,也不替用户做价值判断。
- 用户知道的:视觉/偏好/优先级/成功标准。**不该问的**:代码模式、技术风险、实现路线(那是 plan 的事)。
- **捕获完成标准**:planner 和 executor 拿到 CONTEXT 后,**不再需要追问用户任何问题**。写完自检一遍:还有没有"用户其实在意、但我没问"的口子——漏掉的决策不会消失,它会在执行期变成偏差或返工。

## 灰区识别

- 灰区 = 影响结果且多解的实现决策。从本 phase 的**领域**生成,禁用通用标签("UI/UX 怎么做"✗;"导出是同步阻塞还是后台任务"✓)。
- 数量:2-4 个灰区,每个 ≤2 问;全部清晰 → 明说"无灰区",不硬凑问题。**即便全部清晰也要落一个最小 CONTEXT.md**(记"无灰区,决策已全在项目文档"+ 指向那些文档)——检查器靠 CONTEXT 的存在推进状态机,不落盘就永远卡在 discussing。
- 每个灰区给 3-4 个具体选项,各带一句代价/好处;**不提供"你决定/跳过"选项**——逃逸口会废掉整份决策记录。

## 不重问已决

- 先加载既有决策:STATE 的 Decisions 节、已有 CONTEXT 的 D-NN。已决的**预填**("phase 01 你选了 JWT,沿用还是改?"),不是从头再问;与既有决策冲突 → 显式指出让用户裁决。
- 用户回答中引用的任何文档/spec/issue → 立即读,记入 CONTEXT 的 canonical refs(后续 plan 的验证命令可直接引用)。

## 产出 `.planning/CONTEXT.md`(模板见 mm-gsd-plan/templates/context.md;本地不入库)

- **D-NN 决策要具体**:好 = "卡片式布局,不用时间线";坏 = "现代简洁"——追问到具体为止,模糊决策等于没决策。
- **deferred 兜住范围蔓延**:用户提到的"以后能不能…"全部落进 deferred(不丢、不实施);规划阶段禁止实现 deferred 条目。
- phase 边界来自目标,固定:讨论只澄清 HOW,不加新能力(要加 → 记 deferred)。

## 快速通道

已有 PRD/验收文档/需求单 → 读文档直接抽取决策 + 只问文档**没回答**的灰区,不从零问起。文档与用户口头冲突 → 用户最新口径为准,记一条 D-NN 说明覆盖。
