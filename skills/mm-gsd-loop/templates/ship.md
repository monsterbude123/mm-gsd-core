# SHIP.md 模板(phase 的终态凭据:交付物"被消费"的唯一证据)

只复制下面 ```markdown 块内的内容到 `.planning/<NN>-MM-SHIP.md`。
**验证通过不等于交付。** 没有 SHIP 工件,状态机停在 `completed`,agent 会在验证那一刻宣布整个 phase 完成,
而合并/发布/文档同步那一段没人管。ship 步的落盘物就是这份文件。

```markdown
---
phase: "02"
status: shipped
delivered: <PR 链接 / 合并 commit / 发布单号 —— 写能被第三人核对的具体位置,不写"已合并">
docs_synced: yes
date: <ISO 日期>
---

## 交付内容

<用户/团队现在能消费到的东西。一句话说清"拿到什么、怎么用">,不是提交列表。>

## 交付清单

| 项 | 状态 | 证据 |
|---|------|------|
| 代码合并 | done | <PR 链接或 commit> |
| 测试通过 | done | <命令 + 关键输出> |
| 文档同步 | done | <改动的文档路径;没改写 no 并说明为什么不需要> |
| 用户可见变更已说明 | done | <CHANGELOG / 通知 / 说明文案的位置> |

## 未交付与后续

<如实写:哪些没交付、为什么、留给哪个 phase。status=held 时这里写清阻碍与解法。>
空着比写"无"诚实——被消费这件事必须有人核对过。>

## 回滚方式

<这个 phase 出了事怎么退:revert 哪个 commit / 关哪个 PR / 回滚哪次发布。>
```

维护规则:

- ship 步第一步不是写这份文件,而是**确认东西真的被消费了**:PR 已开且无未解决阻断 / 已合并到目标分支 /
  已发布。写 `delivered` 之前先核对一遍。
- `status: held` 用于"验证过了但交付受阻"(等评审、等发布窗口、缺生产配置)。**受阻就如实写 held**,
  别写 shipped 蒙混——它会让状态机把整个 phase 判成终态。
- 涉及破坏性操作(删数据、force push、动生产、发布)的 ship 步,属于拍板权第 2/3 类,先问用户。
- 下一个 phase 开始前,先确认本 phase 的 SHIP 已落盘且 `status: shipped`,否则状态机会警告你停在验证。
