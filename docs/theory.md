# 理论沉淀

> 这里放**跨实现通用**的规律。具体某个 PR 怎么改的不写在这里,git history 已经记得。
>
> 一条经验该不该进这里,问一句:**换个实现还成立吗?** 不成立就别进,那是实现细节。

---

## T-01 门禁必须自带解法

**规律**:任何"必须满足 X 才准继续"的规则,都要回答一个问题——
**当前执行这一步的人,能不能自己造出 X?**

不能,就产生了死锁:门禁挡住去路,而解除条件的责任在别处。agent 站在原地,无路可走,
只能停下来问人——这恰好是"门禁"想消除的行为。

**实例**:`--plan` 的纪律写"转绿才准进执行环节",而检查器在 `STATE.md` 缺失时 exit 1。
建 STATE 是 loop 的职责,不是 plan/exec 的职责。于是 discuss 结束时 agent 必然卡死。

**落地**:检查器加了 `--init`,任何步骤都能一条命令把 STATE 建起来。门禁要的东西,
必须在这一步之内能造出来。

**可推广**:任何门禁设计评审时问一句"这个条件,执行方满足得了吗"。满足不了就是墙不是门。

## T-02 没有门禁的纪律等于没写

**规律**:写在提示词里、靠模型自觉遵守的纪律,在真实项目里会以各种形式失效——
不是因为模型不听话,而是因为**长上下文里一句话的存活率远低于它的存在感**。

**实例**(同一个 session 内连踩三次):

| 写下的纪律 | 实际失效方式 |
|---|---|
| SUMMARY frontmatter 必须 `status` | 模板里写 `status: complete \| halted`,照抄即非法 |
| PLAN 的 `files_modified` 要精确 | 模板用 `...` 占位,照抄即模糊,并行保护整个失效 |
| SHIP 的 `delivered` 要有证据 | 模板填占位符,门禁把照抄的人拦下 |

三次的共同点:**模板自己没有通过自己的门禁**。所以现在有 `R-05`:
模板必须能通过它对应的检查。

**可推广**:任何"所有文档/代码都要符合的规范",先让规范自己的样例过一遍这道规范。
样例过不了,说明这条规范还没写完。

## T-03 假绿门禁比没有门禁更危险

**规律**:门禁失效时最危险的状态不是"红",是**绿**。
红会逼人排查,绿会让人停止思考。没有门禁时人知道没检查,假绿门禁让人以为有检查。

**实例**:glob 匹配器因为 `**/` 后面多拼了一个斜杠,变成永不匹配。
单文件上限检查因此一路显示绿色对勾、静默空过——
往 skill 里灌 300 行脂肪,它都报"全部在上限内"。

**判据**:任何门禁上线时,**必须先造一个违规输入,证明它真的会红**。
没验证过会红的门禁,不能算门禁。

**判据之二(2026-10-20 补)**:那个违规输入**不能由闸的作者自己产出**。
用自己写的模板造自己的 fixture,等于让两个错误互相印证 —— 模板与闸会一起错,
而它们彼此看着一致,谁也发现不了。

**实例(2026-10-20 已修,留档说明形状)**:验收闸的正则要求小节标题是裸的
`## Human Verification Required`,而 `templates/verification.md` 写的是
`## Human Verification Required(机器验不了,恒发不省略)`。括号后缀让正则永不匹配 ——
**「人工项非空时禁止 passed」这条纪律在任何照模板写的报告上都不生效**,
而自测 fixture 里的标题也是裸的,所以自测永远绿。真正暴露它的是两个外部输入:
emoji 判定符号(`❌ FAILED` 不在封闭词表里,整行被静默丢弃)与模板自带的括号后缀标题。
三样东西同源,只有一样是外面来的。现两处都已修(正则容得下括号后缀、符号表收了 emoji),
自测 fixture 的标题也改成逐字抄模板 —— 但保留这段是为了说明这个形状。

**同一形状在本仓库反复出现**:`gate-selftest.mjs` 头部写着「检查器顶过 713 行」,
逐提交数过是 **699** —— 一条没人核实的注释被后续文档当成事实,一路写进了 CONTEXT 的决策论证。

**可推广**:这条对任何"自动化检查/测试/校验"都成立,不只是本仓库。
lint 规则从没触发过,和没有 lint 规则是同一个状态,只是看起来更好。

## T-04 遥测必须由机器写

**规律**:需要"记得写"的记录系统,产出率趋近于零。而这类系统的全部价值恰恰在数据。

**实例**:第一版观察机制是"agent 每个 phase 手工往 `.planning/mm-gsd-log.jsonl` 追加一行,
不写不阻塞"。跑完一个真实项目后:零个文件。

**替换**:改成检查器每次运行自动写。它是每步必跑的机器门禁,手里已经有
ts / 项目 / 模式 / 推导状态 / 报错 / 退出码——白拿的数据。

**可推广**:要采集的东西,尽量挂在**已经必跑的机器动作**上,不要挂在"记得做"上。

## T-05 门禁要排在早退之后的部分也要能自解释

**规律**:一个命令行工具里,各模式共享一段前置逻辑。如果前置逻辑会提前 `exit`,
那么**排在它后面的模式在特定项目状态下永远跑不到**,而用户看到的现象是
"这个模式好像坏了"——不是报错,是没有输出。

**实例**:`--worktrees` 和 `--stats` 的分块都排在 STATE 检查之后,
而 STATE 检查在 `.planning/STATE.md` 缺失时直接 `process.exit(1)`。
于是任何刚冷启动的项目跑这两个模式,都只会看到"未初始化"。

**落地**:所有模式块移到 STATE 早退之前,并由 `R-07` 检查这个顺序。
配套要求:每个模式的入口必须自己给出行(非空输出),由 `R-08` 检查。

## T-06 编号只在同一个编号空间里才有意义

**规律**:形如 `REQ-01` 的编号是**局部**标识符。跨来源比较编号字面量,
得到的是"编号撞车",不是"需求重复"。误报本身不致命,致命的是它会稀释真信号——
门禁天天报假警,人就学会了忽略它。

**实例**:两个 worktree 的 `REQUIREMENTS.md` 完全不同(md5 都不一样),
各自独立编号,各自都从 `REQ-01` 开始。跨 worktree REQ 比对报了 8 条"需求重复实现"。

**落地**:比较前先确认两个来源是同一份(`R-08` 之外的做法:比对 REQUIREMENTS.md 的哈希),
不同源就降级成提示、不阻塞。

**可推广**:任何"按标识符判断重叠"的逻辑,都要先确认标识符来自同一个命名空间。

## T-07 本地通过不等于正确

**规律**:测试在本地绿,不等于测试是对的。**蒙对和正确在观测上无法区分**——
必须主动去那些本地碰不到的维度上验证。

**实例**(CI 第一次跑就红了):模板自检把沙盒路径硬编码成 `AppData/Local/Temp`(Windows 布局),
并且传的是「相对仓库根」的路径但 cwd 是沙盒。这两件事在 Windows 本地恰好凑成正确的绝对路径——
因为仓库在 D 盘、沙盒在 C 盘,`path.relative()` 跨盘符会直接返回绝对路径。**它蒙对了。**
换到 ubuntu 上,相对层级全错,模板自检立刻报"文件不存在"。

**可推广**:至少在这几个维度主动验证,不要指望本地覆盖:
跨平台(Windows/macOS/Linux)、跨盘符、相对路径与绝对路径、空目录与大文件。
**"我本地是好的"这句话,信息量比它听起来小得多。**

## T-08 门禁的输入坏了,门禁必须自己坏

**规律**:任何门禁都要能区分"检查通过"和"根本没检查"。当门禁的输入本身损坏时
(配置文件解析失败、规则集为空),它必须**硬失败**,不能退化成"没有规则 → 全部通过"。

**实例**:台账 JSON 因为一个漏掉的逗号解析失败,`readJSON` 静默返回 `{}`,
于是 health 输出"**0 条规则门禁全通过**"并 exit 0。
绿色的、成功的、什么都没检查的——这是最坏的组合。

**落地**:health 现在硬读台账原文,解析失败或 active 规则为 0 时直接 exit 1 并说明原因。


## T-09 声称验证了外部系统的步骤,必须读回外部系统

**规律**:一步如果声称自己验证了外部系统的真实状态(npm 有没有这一版、
远端分支推上去没有、文件是否真被部署),它就**必须去读那个外部系统**。
用本地副本的成功返回值推断,是 T-07 的一个具体变种,而且更容易骗过自己 ——
因为它读到的每个中间值都是真的。

**实例**:`mmc release` 第 6 步注释写「从 npm 装回来,用的是刚发出去的那一份」,
代码跑的是 `node <仓库>/bin/mm-gsd.mjs install`。装的全是仓库副本,零网络请求,
npm 上有没有这一版完全不影响结果。而 `npm publish` 的成功行是真的
(上传成功了),只是 npm 有传播延迟,`npm view` 有缓存,staged publish 还会留
`0.0.0-stage` 占位。发布流程宣布成功,用户拿到一个 ETARGET 的安装命令。

清单里的 `source: npm:mm-gsd-core@0.1.0` 是假的。暴露它的是时间戳:
安装 10:05:42,版本真正上架 10:08:16 —— **装在发布之前**。
来源字段和时间戳放在一起看,假绿就无处藏。

**落地**:第 6 步改为 `npm install --prefix <tmp> <name>@<version>` 从 registry 拉,
装完读回清单核对 `source`;发布前用 `npm view` 确认 registry 有这一版,
装回失败回 1 而不是 warn。安装器的来源判据也改成看位置
(`node_modules` 存在、旁边有 `tools/mmc.cjs`)而不是看命令行有没有 `--from-repo`。


## T-10 「结果是 0 条」和「门禁通过」是最危险的两种输出

**规律**:这两种输出的共同点是**长得像正常**。空结果和全绿在屏幕上无法区分,
而它们对应的真实状态是"什么都没发生"和"什么都没检查"。凡是产出计数的步骤,
都必须让「真的是 0」和「没看见」可区分。

**实例**:接报修闭环时连中三次。

1. 上报侧打 `mm-gsd-agent`,拉取侧按 `mm-gsd` 过滤。两处字符串分居两个文件,
   没有任何机制保证一致。结果 3 条只拉到 1 条,输出是"新落 0 条,没有新问题要处理"。
2. 证据提取只认围栏块,匹配不上就写占位符 `(没贴证据)`。而证据门禁只判
   "证据节非空",占位符完全满足 —— **门禁对着假证据说通过**。
3. 证据门禁自己的判据是关键词白名单,使用方的真实复现句子一个词都不匹配,
   于是被判"没有证据"。这条误报只在维护方这边红,使用方提交完就走,
   **永远不知道自己踩的坑没被接住**。

**落地**:拉取不按 label 过滤(避免两处字符串对齐),只取 open,本地按远端号去重;
证据提取退化到缩进块,都没有就写明"没提取到";证据门禁判"有无实质内容"而不是关键词,
放宽后补造两条违规 issue 证明还咬得住。

**推论**:凡是"两个地方必须保持一致"的规则,要么让机器推导,要么让不一致的后果显式可见。
靠人记着的对齐,迟早会对不齐,而且是对齐失败的那一侧没人看见。


## T-11 预算拦下时,先问「这 11 行换来了什么」,再问「怎么删回去」

**规律**:`budget.json` 的「变胖必须有等量删除」在两种情形下会给出错误答案:
一是**为了绕过门禁而删**,二是**把新能力误判成脂肪**。区分它们的不是行数,是
「删掉它之后,下一次同类 bug 会以什么形式回来」。

**实例**:2026-10-19 收到 GitHub #6/#7/#8 三条使用方报修,全是检查器的正则判错。
修完加上自测模式,总行数 3000 → 3011,超 11 行,R-03 拦下。

第一反应是继续砍散文(SKILL.md 已从 300 砍到 272,删了「工件归属边界」「冷启动」
两节的复述)。但砍完还是超 —— 因为这 11 行不是复述,是**新能力**:

- `references/gate-selftest.mjs` 15 条用例,守住三条正则
- R-15 让自测进 `health`,不靠自觉
- `splitDeps` 修「无」被当成依赖(这条是修完 #7 连带暴露的)
- `derived` 读 SHIP 的 status —— 修 `held` 被推成 `shipped`

其中第三条最要命:它堵的是**本系统最核心的假完成**。如实上报 `held` 的 agent
被系统推成 `shipped`,那整个「验证通过 ≠ 交付」的设计就漏了底。这类修复不是
「让工具更完备」,是**把已经存在的漏洞补上**,删掉等于把漏洞装回去。

**落地**:按 `budget.json` 的 `_amend` 条款走 distill —— 把总行数上限提到 3015,
并在 `docs/theory.md` 写清为什么值得(下条)。这不是「嫌麻烦才抬上限」:
抬之前必须能说出**放宽换来了什么可度量的收益**,说不出就不该抬。

**判据**:
- 新增行数换的是**新能力** → 走 distill 抬上限
- 新增行数换的是**已有能力的重复表述** → 删,不许抬
- 新增行数是为了**让门禁能红**(自测用例)→ 算新能力,因为 T-03 要求门禁先证明自己会红

## T-13 门一旦恒红就等于没有门 —— 判据要区分「活工件」与「历史证据」

**规律**:一道门如果它的判红条件**永远满足**,它就不是严,是废。
执行方会学会无视它,而学会无视之后它连当初想防的东西也一起防不住了。

**实例**(2026-10-20):漂移门 `checkDrift` 比工件 mtime 与 CONTEXT mtime。
它只对 live 工件判红时才有意义 —— 但实现上「编辑一次 CONTEXT,该 phase 的
所有历史 PLAN 全部永久变红」,而最常见的 `--plan` 不带参数恰好走全量扫描。
于是只要动过 CONTEXT,这个命令再也回不到绿色。实测 7 份 PLAN 里 2 份恒红。

**为什么不能靠「重新 touch 一下工件」解决**:那是伪造时间戳。
漂移门报的是「决策在工件写出之后又动过」,touch 掉这个红就是让门撒同一个谎。

**落地**:漂移门只对**还有 SUMMARY 未覆盖**的票判红,其余报显式警告。
判活必须读 SUMMARY 的 frontmatter,不能按文件名猜 —— 一份 SUMMARY 可覆盖多张票
(本仓 `02-03-05-SUMMARY.md` 的 `plan: "03,04,05"`),按同名判会把三张已完成的票
全判成未完成。注意 `plan` 字段存的是票号**后缀**,phase 单独一个字段,
拿 `02-03` 去比 `"01"` 是比不上的。

**接受的漏检**:回头重跑一张**已完成**的票时,它的漂移不再被看见。
接受的理由是重跑必须重立 PLAN,新 PLAN 属 live 会被检查;而 phase 的活证据是
`02-VERIFICATION.md`,它比 CONTEXT 新。

**本来考虑过绑内容摘要(指纹)而不是时间戳**,否决。理由两条:
一是它要求 PLAN 里多一个 `context_digest` 字段,而 PLAN 没有任何代码写盘路径
(规划 skill 是散文),只能由 agent 手填 —— 这正是「验收报告不绑代码指纹」那条
排除掉的形状(见下节),按 T-12 是收过路费。二是实测净增检出为零:
本仓 `.planning/` 不进 git,mtime 不存在被伪造的现实场景,摘要能抓的威胁 mtime 已经抓了。

**可复用的判据**:加任何以「文件状态」为输入的门之前,先问一句
**「这个条件会不会永远成立」**。如果会,门是假的,不是严的。

## T-14 门禁自己的失败也要留痕 —— 看不见的失败等于没有诊断入口

**规律**:一条「记录系统」如果只记录它想记的东西,那它记录下来的失败分布是**有偏的**,
而用它做决策的人看不出这个偏 —— 因为偏的那部分正好是「没有消息」的部分。

**实例**(2026-10-20):本机遥测 `~/.agents/mm-gsd-runs.jsonl` 4971 条,
真实项目 4956 条、失败 1822 次(36.8%)。但逐条查:**1770 次失败(97%)在遥测里
errors/warnings 全空** —— 门红了,日志里零消息。

根因很朴素:检查器有 8 处早退路径直接 `console.log` + `process.exit(1)`,
**不经过 `err()`**,原因只进了 stdout,没进结构化遥测。

后果是 observe 环自己瞎了:
- `--stats` 承诺报「高频报错类型排行(最该修的地方)」—— 而 97% 的失败没有类型可言;
- 「同一项目反复失败」这个死锁信号还在,但配不出原因,抓不到卡在哪一步。

**修法有两条,缺一不可**:
1. **早退路径也走统一出口**(`die(msg, fix)`):打印给人看的同时把原因写进遥测。
   只改打印不改记录,遥测照样瞎。
2. **自测产生的失败要与真实失败分开**。自测沙箱里的失败是**正常的**(那是在故意造失败),
   混进排行会把诊断入口淹掉。标记由**跑沙箱的一方声明**(`GSD_SANDBOX=1`),
   不由被观测方猜路径 —— 用户自己建在临时目录里的真项目不该被误排除。
   历史记录没有标记,靠路径特征作兜底。

**副作用值得记**:把 `console.log` 换成 `die()` 之后,R-04「模式的分块里没有任何输出」
当场判红 —— 门禁抓对了,是我改的。修法是让检查器认识 `die`(它内部 console.log 后退出),
**不是**把 `die` 改回裸 exit(那样遥测又瞎了)。两个门冲突时,先问哪个门在防真问题。

**可复用的判据**:给门禁做统计之前,先看**失败样本里有多少带原因**。
带原因的占比太低,这个统计就不能用来决定「下一步修哪」——
它已经被自己的实现方式偏了,而且看不出来。

## T-11b 拦住肥胖之后要给出改造方向,不是只判红

**规律**:预算门禁只回答「哪里错了」不回答「那我该拆什么」时,执行方只剩两个选择:
抬上限,或者硬删。前者毁掉门禁,后者毁掉内容 —— 两种都发生过(见 T-11 的实例)。

所以 `check-budget` 拦红时必须输出**改造指引**,实现见 `tools/fat-advice.mjs`。

**references 化的具体形态**(用户定,2026-10-20):

| | 留什么 | 去哪 | 依据 |
|---|---|---|---|
| **骨架** | 入口、状态流转、装配(import 与注册) | 留在核心文件 | 主流程每行都要读的 |
| **按需引用的内容** | 判定规则表、契约表、正则表、模板 | `references/<契约名>.mjs` 或 `tools/` 独立模块 | **只在特定分支才用到**,主流程不需要每行都读 |

**「按需引用」的机器判据**:主文件只 `import` 并调用,不复制。
复制就变成两份会分叉的真相 —— 那正是本仓 `gate-cases.json` 登记 `check-template-gates`
时记下过的失败形状。

**三种形状必须给三种指引**,一刀切说「references 化」是废话:
- **主文件超限** → 完整三步(骨架留核心 / 内容进 references / 只 import 不复制)
- **`references/` 内超限** → 它**已经**是抽出去的那部分,再抽没有落点。
  该问的是「它是不是被误当成垃圾桶」—— 拆的依据必须是「判据自成一族」,不是「这里塞得下」
- **散文(SKILL.md)超限** → 没有调用点,references 化对它不成立。先砍复述;
  只有「读的人不必每次读全」的部分才拆,并由正文显式指路

**判据不变**:拆之前先问 T-11 那一句 ——「删掉之后,下一次同类问题会以什么形式回来」。
答不上来说明它是新能力,该抬上限不该拆。


## T-12 会逼人做等价交换的硬约束,是收过路费不是防肥胖

**规律**:一条约束一旦开始**逼执行者为它做等价交换**,它就从约束变成了税。
判据很具体:**为了满足它而做的删除,是去脂肪,还是为计数器好看?**
两者外部行为一样,动机不同,只有写的人知道 —— 而他往往说不清,因为当时确实是在「两难」。

**实例**:`budget.json` 的 `totalLines` 硬顶(3000 → 3015)。来源不是 GSD ——
GSD 全仓零预算机制、72 个技能、光一个 debug 工作流就 293 行。它是本仓库为了实现
「让 gsd 不在肥胖」这个目标自己加的,加的时候没想过它会怎么影响写文档的人。

实际发生的:

| 改动 | 新增 | 为凑行数做的事 |
|---|---|---|
| 报修闭环进 SKILL.md | +25 | 砍「工件归属边界」「冷启动」两节的复述 |
| verify 纪律进 exec | +2 | 把失效模式第 1、4 条合并(两者原是不同的事) |

这两处的删除**都不是脂肪**。它们让文档更密、更难读,换来的是一个计数器好看。

**关键区别**:全局总量硬顶逼的是**跨文件等价交换** —— 你在这里加,必须在那里减,
而两者往往无关。单文件上限逼的是**同一件事别写太长**,这才是它真正想防的。

**落地**(2026-10-19):`totalLines` 从硬顶降为**参考线**,超过只提示不拦人。
当时保留两条硬门禁,因为它们防的是真问题:

- `fileCaps` —— 单个文件无限膨胀
- `maxTotalFiles` —— 该合并而不是新增

**补记(2026-10-26)**:「保留两条硬门禁」这个判断后来被推翻 —— 那两条硬门禁自己也成了
等价交换的驱动器,还多了一层副作用(把功能塞进语义不对的地方)。两条硬门禁已退役,见 T-16。

**推论**:约束设计要看**它约束的是什么**。跨维度的总量上限最容易变成等价交换的
驱动器,因为它把不相关的文件绑在了一起。反过来,一个只约束「这件事本身别太大」
的上限,几乎不会诱发扭曲行为 —— 它的压力方向和作者的意图是同一个。

## T-15 让人手动做一次的动作,别顺手自动化 —— 自动化会让「做过没有」不可追溯

**规律**:有些动作的价值恰恰在于「人明确地做了一次」。它是一次**重置/确认**,
不是一次数据处理。自动化之后,「到底做没做过」这件事就没人答得出来了。

**实例**(D-05,用户明确要求):每次安装 mm-gsd 后**手动**清一次本机监控日志
`~/.agents/mm-gsd-runs.jsonl`。日志记的是**上一次安装之前**的使用历史,装新版本后
那些记录对应的是旧版本的门禁语义,继续留着会让 `--stats` 混进已经改掉的行为。
手动清是一次「重新开始计数」的动作;自动清(安装时截断)会让「清过没有」不可追溯 ——
而统计口径已经变了这件事,本来就需要有人知道。

**判据**:一个动作要不要自动化,问一句:**自动化之后,这件事做没做过还能不能被查出来?**
答不上来就别自动化。可追溯性没了的自动化省下的是几十行代码,赔上的是「出了事没人知道
是从哪一步开始的」。

**为什么写进规律而不是写进 SKILL.md**:散文纪律一旦有了门禁化的对应物,半年后一定会有人
把它当待办项实现掉 —— 「顺手加个开关」看着是进步,实际是把一条有意的人工动作抹掉。
所以要连同**「为什么不自动化」**一起记在这里。程序里没有清理开关,安装时也不自动截断,
这是决定,不是待办。

## 明确排除的做法(对照原 GSD 抄作业时留下的)

不是规律,是决策。记在这里是因为**只记规律的地方会让人反复重新提同一个想法**。
每条都写清「什么条件下才值得重开」—— 没有重开条件的决策,半年后一定会被当成遗漏。

### 验收报告不绑代码指纹(GSD 第二层:代码变更即 stale)

GSD 的 `covered_digest` + STALE 路由会让「验证之后又改了代码」的旧验收自动作废。
mm-gsd **不做**:它需要「phase 范围内文件 × git 时间」的真实机器,而当前没有 phase 级
代码作用域。硬加会退化成「要求 agent 手工维护指纹字段」—— 按 T-12,那是收过路费。
**重开条件**:真的出现「验证后改了代码没复验」的事故,而不是设想中的可能。

### 验收不做外生 backstop 标签(GSD 第五层)

GSD 实测:盲区检查上验收者给出自信 PASS 的比例约 100%(平均自信度 0.93);
问它「你确定吗」只能降到 67%,改用**外生**标签(人在写规格时就打的标记)才降到 17%。
原因是一句话:**置信门禁够不到模型感觉不到的盲区**。

mm-gsd **不做**:这套成立的前提是规格阶段有一个人类作者愿意打标签。而 mm-gsd 的 PLAN、
诊断报告、验收报告**都是 agent 自己写的** —— 外生标记的来源根本不存在。照搬只会退化成
「让 agent 自我声明这里我不确定」,而自我声明正是那个 67%,基本无用。
**重开条件**:mm-gsd 出现「规格由人写、agent 只负责实现」的分工,或者这个 17% 的差距
在真实项目里反复造成漏判。

## T-16 体积硬顶退役:它防的不是肥胖,是「把功能塞到不对的地方」

**触发**:2026-10-26,维护者判定 mm-gsd 自己的体积硬顶(`fileCaps` + `maxTotalFiles`)
「没啥太大的意义」,要求移除。执行时立刻看见硬顶在干什么:为了加一个「显式校验计划」
的入口,本该新写一个模块,却被迫把代码挤进已有的 `artifact-ledger.mjs`、
把检查器里 17 行有信息量的注释压掉、把提示词模板拆去别处 —— 全是为了「不破 700」。

**规律**:硬顶会**改写作者的行为目标**。作者本来要回答「这份计划能不能开工」,
被硬顶改写成「怎么让改动不破上限」—— 于是交付物是等价交换,不是能力。
T-12 观察到它的第一层副作用(跨文件等价交换),T-16 观察到第二层:
**上限会让人把功能塞进语义不对的地方**;塞得进,就没���再问「这里该是什么」。

**落地**:
- `budget.json` 去掉 `fileCaps` 与 `maxTotalFiles`;`totalLines` 早已只是参考线,保留。
- `check-budget` 从「超限就红」变成「只报不拦」:总行数、按族分组、最大三个文件。
- R-03(体积硬顶)从台账退役,基线同步移除 —— 只删台账不算(见 `tools/rule-baseline.mjs` 文件头)。
- 随硬顶一起退役的还有 `tools/budget.mjs` 里的「超限诊断」(`fatAdvice`):没有上限就没有
  「超了怎么办」,留着它就是一份没人调用的说明书 —— 而本仓最忌讳死代码。
- 「想拆文件时该看哪」的知识没丢:它在 T-11 里,那才是知识的正确位置。

**保留什么**:门禁还在,只是换了它要回答的问题。`check-budget` 现在证明的是
「体积统计用的匹配器是好的」(匹配器坏掉时静默不匹配 = 统计假绿),R-09 继续驱动它;
`budget.json` 的 `systemGlobs` / `docGlobs` 继续用,只是用来**分组报告**而不是设上限。

**判据**:一个约束如果开始改变**交付物的形状**(而不只是判定它合不合格),
它就该被怀疑。约束防的是真问题还是防计数器,问一句「删掉它,下一次同类问题会以什么形式回来」
—— 答不上来,就是收过路费。
