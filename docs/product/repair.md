# 点修与报修

本篇合并两个相关能力域:**点修**(已交付内容的快速修复通道)与**报修**(问题的登记与闭环)。

## 点修:已交付 phase 的单条细节没做好

验收或使用中发现某个已交付 phase 有单条细节缺陷,走**点修**:在原 phase 上挂一张快速修复票(R 票),修完重验 —— **不开新 phase**。

- 看板总览里修复中的点修票有计数(「点修票挂起」),phase 详情面板里也标「点修」;收口后计数清零。
- 批注类型选「验收不过」会让看板与检查器提醒走点修分流 —— 单条细节缺陷走点修;方向性问题不是缺陷,回讨论重开决策。

## 报修:把使用中的问题变成可闭环的账

使用方 agent 发现工具本身的问题,走随包分发的报修入口:

```bash
npx mm-gsd-core report "<标题>" --evidence "<复现命令或报错>"
```

- **没证据不给建**:报修必须带复现命令或报错,否则入口拒绝 —— 防止「感觉不对」变成账面问题。
- 报修落**本地账**(项目里的 issue 登记文件),不直接动代码。

## 闭环:登记 → 修复 → 关闭 → 复发监测

- **修复**:修完标记已修并跑全部门禁 —— 门禁不绿不许标已修。
- **关闭**:只关闭已修且带远端编号的账;本地与远端状态不同步是常态,关闭时去远端读回真实状态,不假设同步。
- **复发监测**:关掉的账如果同一根因又以同一把尺子出现(失败指纹逐字对上,不是「标题看着像」,也不是手填的「已验证」),自动拉回未解决并记下复发日期。
- 这套循环唯一的成败指标是**同一根因二次出现率**:少关、装样子、把关掉当成终点,都会让它变难看 —— 它量的是沉淀质量,不是人的产出。样本不足 5 时只报原始比例,不报百分比(一个样本能刷出 100%,那是噪声不是指标)。

## 边界

- 点修管「单条细节」,不管「方向不对」:后者是产品取舍,回讨论环,不进修复通道。
- 报修入口只登记、不修复;修复走流程票,与任何其他票同一套四件套与验证契约。
