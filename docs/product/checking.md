# 校验

整个工具只有一个状态检查器,多种模式,全部经由 `mm-gsd check` 进入。它是「门禁」的实现:退出码 0 = 转绿,非 0 = 有违规,可以直接接 CI 或宿主 hook。

## 模式族:什么时候用哪个

| 场景 | 命令 | 做什么 |
|---|---|---|
| 项目冷启动 | `mm-gsd check --init "<项目目标>"` | 建状态文件 —— 任何步骤卡住都能一条命令救回来,门禁自带解法 |
| 每步收尾 | `mm-gsd check` | 工件契约 + 状态推导 + 交付缺口 —— 声明不能说谎,状态从工件推导出来与声明比对 |
| 计划落盘后 | `mm-gsd check --plan` | 计划的机械合规:四件套齐不齐、失败方向、文件清单、任务预算、决策核销、同批并行票不撞文件、引用路径真实存在 |
| 想现在就知道能不能开工 | `mm-gsd check --plan-check <计划文件>` | 显式校验一份计划:机器判据 + 预审工件合成一个结论(退出码 0 = 能开工);预审还没做时,把该派的只读复核提示词直接打印出来,照抄即可 |
| 规划前 | `mm-gsd check --phases` | 算执行波次:依赖成环直接报错(没有合法执行顺序),同波次文件清单必须零重叠 |
| 并行前 | `mm-gsd check --worktrees` | 跨工作树的文件与需求冲突检查 |
| 模板改动后 | `mm-gsd check --templates` | 模板结构契约自检 |
| 不知道下一步 | `mm-gsd check --routes` / `--route <阶段>` | 每个技能写清了自己的下一步;某阶段该读什么、本项目的门禁速查(现场从台账读出,不手写) |
| 诊断 | `mm-gsd check --stats` | 读遥测:门禁失败率、同一项目反复失败次数、高频报错排行(`--stats --tools` 看工具维度,`--all` 看全部项目) |

## 快检与全量分级

门禁体检分两档,**慢门禁不悄悄跳过 —— 跳过时点名**:

- **快检**:逐次提交跑,只跑便宜的门禁;
- **全量**:批次与 phase 收尾跑一次,包含模板自检、门禁活性等慢检查。

配套纪律:一批票全部落地后跑一次全量,失败**一次修完**再跑,不做「改一处跑一次」的逐次循环 —— 票级验证只跑本票的便宜检查,全量套件永远属于批次,不属于单票。

## 跨平台:换行与 LF

Windows 上检出同一份仓库,工作区里可能是 CRLF、可能是 LF,也可能是两种混在一起。
这节只给**判断与配置**的办法:怎么认出这是行尾问题、怎么配、先怎么量体量再动手。
工具不改你的文件 —— 配置写在你自己的仓库里,改不改由你决定。

### 判据:怎么认出是自己的行尾出事

**症状是你自己写的脚本、自建的工件按行比对出错**:同一份文件在编辑器里看着完全一样,
提交后却整文件全变;脚本按行读、按行比对时错位或匹配不上。这时候该怀疑行尾。

**但这不是 mm-gsd 的模板抽取出错。** 工具侧的模板抽取本来就同时认 CRLF 和 LF,CRLF 的模板一样抽得出 markdown 块。
出问题的是你自建工件的行尾,不是工具读模板的方式。

### 命令:推荐档与条件档

**推荐档 —— 只在提交时转换**(Windows 上实测安全的一档:状态保持干净,索引里仍是 LF)。
只写当前仓库的 `.git/config`,不改全局设置:

```bash
git config core.autocrlf input
```

**条件档(前提:工作区已经是 LF)** —— 只有工作区现在已经是 LF 时切这一档才安全;
配套是先加 `.gitattributes` 再 renormalize:

```bash
git config core.autocrlf false
```

代价:在 Windows 默认克隆上切到 `core.autocrlf false` 这一档,工作区会整片变脏(实测一个 5 行文件报成 5 增 5 删);
没有 `.gitattributes` 时 renormalize 还会把索引写成 CRLF,等于把 CRLF 提交进仓库。

**量体量分两次,两次看的不是同一份差异:**

**改设置之前**先量工作区那份:`git diff --stat` —— 它比的是工作区相对索引的差异,告诉你现在脏不脏。

`git add --renormalize .` 之后,差异落在**暂存区**,改看 `git diff --cached --stat` ——
这份才告诉你到底有多少文件会被改写;(此时再去看工作区那份差异会显示空,容易以为「没变化」)。

### 适用范围

`.gitattributes` 只适用于全新克隆、或没有 CRLF 历史的仓库:它靠的是从检出那一刻就按规则生成行尾。

**老仓库(已经有 CRLF 历史的)先 renormalize 再量体量,决定要不要继续** ——
顺序不能反:先 renormalize 会把差异堆到暂存区,先量体量才知道改写面有多大。

### 边界

- **本仓不会替你改写工作区文件**,也不批量重写既有文件:改行尾是不可逆操作,由你自己决定。
- **只对本仓库生效**:配置写进当前仓库的 `.git/config`,不用全局开关,也不碰用户主目录下的配置文件。
- 本仓工作区本身就可能是**混合行尾**(LF 与 CRLF 并存),不是每个文件都一样。
  查自己的现状用 `git ls-files --eol`:`i/` 是索引里的行尾,`w/` 是工作区的行尾。

## 边界

- 检查器只核对契约与推导,不替你写工件;冷启动之外任何模式都不修改项目文件。
- 计划校验里「前提存在性」也核对:票里引用的路径必须真实存在(票自己产出的除外)—— 票站在假前提上,执行端只会照着编。
- 「显式校验」不等于自动修:它给「能不能开工」的结论与逐条发现,改法归计划,拍板归讨论。
