# 校验

整个工具只有一个状态检查器,多种模式,全部经由 `mm-gsd check` 进入。它是「门禁」的实现:退出码 0 = 转绿,非 0 = 有违规,可以直接接 CI 或宿主 hook。

## 模式族:什么时候用哪个

| 场景 | 命令 | 做什么 |
|---|---|---|
| 项目冷启动 | `mm-gsd check --init "<项目目标>"` | 建状态文件 —— 任何步骤卡住都能一条命令救回来,门禁自带解法 |
| 每步收尾 | `mm-gsd check` | 工件契约 + 状态推导 + 交付缺口 —— 声明不能说谎,状态从工件推导出来与声明比对 |
| 计划落盘后 | `mm-gsd check --plan` | 计划的机械合规:四件套齐不齐、失败方向、文件清单、任务预算、决策核销、同批并行票不撞文件、引用路径真实存在 |
| 想现在就知道能不能开工 | `mm-gsd check --plan-check <计划文件>` | 显式校验一份计划:机器判据 + 预审工件合成一个结论(退出码 0 = 能开工);预审还没做时,把该派的只读复核提示词直接打印出来,照抄即可 |
| 规划前 | `mm-gsd check --phases` | 算执行波次:依赖成环直接报错(没有合法执行顺序),同波次文件清单必须零重叠 |
| 并行前 | `mm-gsd check --worktrees` | 跨工作树的文件与需求冲突检查 |
| 模板改动后 | `mm-gsd check --templates` | 模板结构契约自检 |
| 不知道下一步 | `mm-gsd check --routes` / `--route <阶段>` | 每个技能写清了自己的下一步;某阶段该读什么、本项目的门禁速查(现场从台账读出,不手写) |
| 诊断 | `mm-gsd check --stats` | 读遥测:门禁失败率、同一项目反复失败次数、高频报错排行(`--stats --tools` 看工具维度,`--all` 看全部项目) |

## 快检与全量分级

门禁体检分两档,**慢门禁不悄悄跳过 —— 跳过时点名**:

- **快检**:逐次提交跑,只跑便宜的门禁;
- **全量**:批次与 phase 收尾跑一次,包含模板自检、门禁活性等慢检查。

配套纪律:一批票全部落地后跑一次全量,失败**一次修完**再跑,不做「改一处跑一次」的逐次循环 —— 票级验证只跑本票的便宜检查,全量套件永远属于批次,不属于单票。

## 跨平台:换行与 LF

Windows 上同一仓库可能 CRLF / LF 混杂,症状是「文件没改却整文件全变、按行比对错位」。工具侧的模板抽取本来就同时认两种行尾,出问题的是自建工件的行尾 —— 判据、推荐配置档与量体量步骤见仓库根 README 的「跨平台:换行与 LF」一节;工具不改你的文件,配置写在你自己的仓库里。

## 边界

- 检查器只核对契约与推导,不替你写工件;冷启动之外任何模式都不修改项目文件。
- 计划校验里「前提存在性」也核对:票里引用的路径必须真实存在(票自己产出的除外)—— 票站在假前提上,执行端只会照着编。
- 「显式校验」不等于自动修:它给「能不能开工」的结论与逐条发现,改法归计划,拍板归讨论。
